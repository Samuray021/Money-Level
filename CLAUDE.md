# CLAUDE.md — постоянные правила Claude Code для Money Level

## Назначение
Money Level — офлайн-дружественное мобильное PWA для личных финансов. Внешняя оболочка использует мемы, юмор, компаньона и игровые элементы; внутри — точный и переносимый финансовый движок. Пользователь владеет продуктом, кодом и решениями.

## Источники истины и пути
1. `docs/MONEY_LEVEL_TECH_SPEC_v1_1.md` — требования продукта, финансовые инварианты, архитектура, эталонные тесты, критерии релиза.
2. `docs/CLAUDE_ATOMIC_BACKLOG_v1_1.md` — точные задачи `ML-001`–`ML-100`, зависимости и критерии приёмки. Для исполнения задачи использовать именно этот ID.
3. `PROGRESS.md` — подтверждённый прогресс, результаты проверок и блокеры. История прогресса — не источник продуктовых требований.
4. `docs/CLAUDE_START_PROMPT.md` — инструкция для старта первой задачи; не заменяет ТЗ.

Если источники противоречат друг другу: финансовые инварианты и безопасность из ТЗ важнее; следом идут критерии приёмки ТЗ; затем бэклог. Не разрешать противоречия догадками: создать запись в `PROGRESS.md`, описать вопрос и безопасное решение. В частности, в разделе 28 ТЗ есть крупные фазы с ID `F0-*`, но при работе с атомарным бэклогом использовать `ML-*`, не считать их одинаковыми идентификаторами.

## Первый запуск
- Прочитать `CLAUDE.md`, затем ТЗ, атомарный бэклог и `PROGRESS.md`.
- Определить первую задачу `ML-*` со всеми выполненными зависимостями; изначально это `ML-001`.
- Проверить структуру рабочего дерева и git status, чтобы не перезаписать пользовательские правки.
- Если явно не дано разрешение на серию задач, выполнять одну задачу за запуск. Если серия разрешена, строго по одному ID, с тестами и фиксацией прогресса после каждого ID.

## Архитектура
- TypeScript в strict-режиме; монорепозиторий pnpm; веб-приложение React + Vite.
- Пакеты и направления зависимостей — из раздела 21 ТЗ. Финансовый домен не зависит от React, DOM, IndexedDB и движка мемов.
- Отдельные пакеты/адаптеры для финансов, аналитики, реакций, UI и инфраструктуры; не смешивать логику расчётов и визуальные эффекты.
- В MVP хранение локальное с надёжным экспортом/импортом; банковские подключения, реальный перевод денег, серверная синхронизация и генеративный AI не входят в MVP.
- UI на русском (`ru-RU`) с подготовкой к локализации. Стартовая валюта выбирается при онбординге, в MVP одна базовая валюта для всех счетов.

## Обязательные финансовые инварианты
- Хранить деньги в целых minor units, для RUB — копейки. Не использовать двоичный float для денежных сумм.
- Баланс выводить из записей журнала. Не хранить независимый баланс, способный разойтись с журналом.
- Начальный остаток изменяет баланс, но не является доходом.
- Перевод между собственными счетами не меняет совокупный баланс и не является доходом/расходом.
- Резерв на цель не изменяет общий баланс и не считается расходом; влияет на доступные для трат средства.
- Изменение или удаление операции корректно пересчитывает историю и отчёты. Повтор команды с тем же idempotency key не списывает деньги повторно.
- Все эталонные тестовые случаи `TC-FIN-*` из раздела 27 ТЗ должны совпадать до копейки.
- Мемные события запускаются только после успешного сохранения финансовой операции и никогда не изменяют финансовые записи.

## Приватность и UX
- Никаких реальных денег, платежных API или банковских секретов в MVP.
- Не отправлять финансовую историю в сторонние сервисы без отдельно спроектированного согласия и задачи.
- По умолчанию не включать реальные суммы/имена счетов в экспортируемые мемные карточки.
- Юмор, мат, звуки и анимации должны отключаться. Учитывать reduced motion, доступность и понятные подписи финансовых действий.
- Шутки не мешают вносить записи, не маскируют ошибки и не высмеивают реальные финансовые затруднения.

## Процесс выполнения каждой задачи
1. Назвать ID, связанные разделы ТЗ, зависимости, инварианты и затрагиваемые файлы.
2. Сделать минимальную реализацию без незапрошенных функций из последующих этапов.
3. Добавить unit/integration/e2e тесты по характеру задачи; при изменениях денег — числовые регрессионные тесты.
4. Запустить доступные `lint`, `typecheck`, `test`, `build` (если команды существуют на текущем этапе). Сообщать реальные результаты и причины пропуска, не писать «прошло», если не запускалось.
5. Проверить `git diff` и отсутствие чувствительных данных. Обновить `PROGRESS.md`: статус, SHA коммита (если создан), проверки, замечания и следующая задача.
6. Создать небольшой понятный коммит в рабочей ветке, если Git доступен и пользователь разрешил коммиты.
7. Следующую задачу начинать только при выполнении зависимостей и наличии разрешения на продолжение.

## Безопасность Git и внешних действий
- Не делать force-push, rebase чужих веток, destructive clean/reset или изменение `main`/`master` без явного согласия.
- По умолчанию работать в отдельной ветке и готовить Pull Request для проверки.
- Не делать деплой в production, не вводить API-ключи, не подключать платные сервисы без отдельного согласования.
- Никогда не добавлять секреты и реальные финансовые данные в Git или тестовые фикстуры.
- После остановки/перезапуска проверять реальное состояние файлов, коммитов и тестов; не доверять одному флажку в `PROGRESS.md`.

## Формат короткого отчёта
- `Задача: ML-XXX`
- `Изменено:` список файлов и краткая цель
- `Проверки:` команды с результатом PASS/FAIL/NOT RUN
- `Приёмка:` что подтверждено, что нет
- `Git:` ветка, коммит или причина отсутствия
- `PROGRESS.md:` обновлено / нет с причиной
- `Далее:` следующий допустимый ID или блокер

## Правило релиза
Не называть продукт готовым до прохождения критериев MVP в разделе 29 ТЗ. После MVP не начинать `ML-092`–`ML-100` без отдельного разрешения.
